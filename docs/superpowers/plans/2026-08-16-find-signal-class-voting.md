# `find_signal` 类别滑动窗口投票设计

## 目标

修改 `src/find_signal/src/rknn_ros.cpp` 的类别确认机制：不再要求连续 5 帧识别出
同一类别，而是维护最近 5 个处理帧的滑动窗口。只要食品、日用品或电子产品中的任一类别
在窗口内出现至少 3 次，就向 ROS 的 `/signal_class` 发布该类别。

本阶段只输出设计方案，不修改实现代码。

## 当前行为

当前节点使用 `streak_class_id_` 和 `streak_count_` 统计连续相同类别，并使用
`last_confirmed_class_` 保存确认结果：

- 类别变化时连续计数从 1 重新开始；
- 无检测框或 OCR 文本无法分类时清空连续计数和确认结果；
- 连续帧数达到 `confirm_frames_`（默认 5）后确认类别；
- 确认后每个仍有检测框的处理帧都会继续发布类别，满足下游按消息时间判断数据新鲜度的
  要求。

这种方式无法容忍 5 帧中夹杂少量 OCR 抖动。例如 `0, 0, 1, 0, 0` 虽然明显以类别 0
为主，却始终不能达到连续 5 帧。

## 投票语义

### 窗口与票数

- 窗口固定保存最近 5 个已经取回并处理的推理结果，先进先出；
- `classfy` 返回的有效类别 `0`、`1`、`2` 各计一票；
- OCR 文本无法分类或该帧没有检测框时，向窗口写入 `-1`。`-1` 占用窗口位置以淘汰
  旧票，但不参与任何类别的获胜计数；
- 每加入一个结果后，若窗口超过 5 个元素，就删除最早的元素；
- 任一有效类别票数达到 3 时，该类别成为当前窗口的获胜类别；
- 不要求先填满 5 个元素，启动后的前三个结果相同即可在第三个结果处首次发布；
- 5 个位置中不可能有两个有效类别同时达到 3 票，因此不需要额外的平票规则。

示例：

| 最近结果 | 决策 |
| --- | --- |
| `0, 0, 0` | 类别 0 达到 3 票，发布 0 |
| `0, 1, 0, 2, 0` | 类别 0 有 3 票，发布 0 |
| `0, 1, 0, 2, -1` | 没有类别达到 3 票，不发布 |
| `-1, 2, 1, 2, 2` | 类别 2 有 3 票，发布 2 |
| `0, 0, 0, 1, 1` 后再加入 `1` | 淘汰最早的 0，窗口为 `0, 0, 1, 1, 1`，改为发布 1 |

### 发布行为

每个处理帧加入窗口后都重新统计票数，而不是把一次获胜永久锁存：

- 当前窗口存在 3 票多数时，若当前帧有检测框，则持续发布获胜类别；
- 当前窗口没有 3 票多数时，不发布 `/signal_class`；
- 当前帧没有检测框时，仍以 `-1` 更新窗口，但沿用现有流程直接返回，不发布
  `/signal_detection` 或 `/signal_class`；
- 当前帧有检测框但 OCR 文本无法分类时，照常发布 `/signal_detection`。加入 `-1` 后，
  如果窗口内的历史有效结果仍构成 3 票多数，可以继续发布该多数类别；
- 获胜类别发生变化时立即切换发布内容，不额外要求连续确认。

这样可以保持 `/signal_class` 的持续新鲜度，同时避免已经离开最近 5 帧窗口的旧结果继续
影响输出。

## 实现方案

仅对 `SignalDetectionNode` 内的类别确认状态做局部替换，OCR、检测框选择、NPU 线程池和
ROS 话题保持不变。

### 常量和成员

在匿名命名空间中定义固定常量：

```cpp
const int kVoteWindowSize = 5;
const int kVoteThreshold = 3;
```

增加 `#include <deque>`，并用以下状态替换连续帧状态：

```cpp
std::deque<int> class_vote_window_;
int voted_class_id_;
```

删除不再需要的成员：

- `confirm_frames_`；
- `streak_class_id_`；
- `streak_count_`；
- `last_confirmed_class_`。

现有 `~confirm_frames` 参数只服务于连续帧机制，改为固定 5 帧窗口后不再读取，并从
`NodeConfig` 和项目指南中删除。仓库内没有 launch 文件设置该参数，因此不会影响当前
启动配置。本次不新增可配置参数，避免出现窗口不是 5 或阈值不是 3、与需求语义不一致的
情况。

### 投票更新函数

把 `update_class_streak(int class_id)` 替换为职责单一的
`update_class_vote(int class_id)`：

1. 将 `class_id`（包括 `-1`）追加到 `class_vote_window_`；
2. 当窗口长度大于 5 时弹出最早结果；
3. 统计窗口中 `0`、`1`、`2` 的出现次数；
4. 找到首个达到 3 票的类别并写入 `voted_class_id_`；
5. 没有类别达到阈值时将 `voted_class_id_` 设为 `-1`；
6. 仅当获胜状态发生变化时记录 INFO 日志，普通窗口状态使用现有节流日志，避免逐帧刷屏。

类别范围固定且只有 3 个，直接使用三个整数或 `std::array<int, 3>` 计数即可，不引入 map、
通用投票器或额外源文件。

### `publish_result` 调整

处理顺序保持为：

```text
取最大文本框
  ├─ 无框：update_class_vote(-1) 后返回
  └─ 有框：发布 /signal_detection
             ├─ classfy(text)
             ├─ update_class_vote(class_id)
             ├─ 输出节流的窗口票数日志
             └─ voted_class_id_ != -1 时发布 /signal_class
```

不改变最大框选择、检测框中心坐标计算或消息类型。

### 生命周期

沿用当前节点的启停语义：`~set_enabled` 只暂停或恢复业务处理，不额外清空识别状态。
因此暂停期间窗口不变化，恢复后的新结果会按 FIFO 规则逐步替换暂停前的结果。本次不顺带
修改线程池在途结果或节点启停行为。

## 文件变更范围

- 修改 `src/find_signal/src/rknn_ros.cpp`：用 5 帧、3 票滑动窗口替换连续帧确认；
- 修改 `docs/guides.md`：将“连续 5 帧防抖”和 `~confirm_frames` 参数说明更新为固定
  5 帧、3 票机制；
- 不修改 OCR Python 旧实现、消息定义、launch 文件及下游 `ourgoal`。

## 保持不变的行为

- 每帧只使用面积最大的 OCR 文本框做分类；
- 类别映射仍为 `0=食品`、`1=日用品`、`2=电子产品`；
- `/signal_detection` 仍在有最大框时立即发布，不受类别投票限制；
- `/signal_class` 的类型、话题名和队列大小不变；
- 获得当前窗口多数票后仍逐帧发布，而不是只发布一次；
- `thread_count`、模型路径、可视化及节点启停逻辑不变。

## 测试与验收

### 决策序列

通过日志和 `/signal_class` 监听验证以下序列：

1. `0, 0` 不发布，第三个 `0` 到来后发布 0；
2. `0, 1, 0, 2, 0` 在最后一帧发布 0，证明结果无需连续；
3. `0, 1, 0, 2, -1` 不发布；
4. `-1, 2, 1, 2, 2` 发布 2，证明无效结果占窗口但不计票；
5. 从 `0, 0, 0, 1, 1` 再输入 `1`，验证最旧的 0 被淘汰并切换为发布 1；
6. 已有多数票时输入一次其他类别或 `-1`，只要最近 5 个结果仍保有 3 票就继续发布；
7. 多数票被窗口淘汰后立即停止发布，不继续使用旧确认类别；
8. 连续有检测框但 OCR 分类失败时，`/signal_detection` 行为保持不变；无框时两个话题均
   不发布。

### 构建与运行

- 构建 `find_signal`，确保 C++11 编译通过且没有遗留的连续计数成员引用；
- 在 ROS 环境启动节点，使用 `rostopic echo /signal_class` 检查发布结果；
- 同时观察 `/signal_detection`，确认投票改动没有影响检测框消息；
- 启用、禁用再启用节点，确认服务行为与修改前一致；
- 在 RK3588 实机视频流中加入偶发 OCR 错判，确认 5 帧内 3 个一致结果可以稳定输出。

## 验收标准

- 最近最多 5 个处理结果中，任一有效类别达到 3 票时发布该类别；
- 结果可以不连续，且第三个相同结果到来时即可发布；
- 无类别达到 3 票时不发布旧类别；
- 无效识别能够推动窗口淘汰旧票，但自身不能获胜；
- 发布话题格式、检测框发布、OCR 推理和节点启停行为无回归；
- 实现改动限定在类别决策及对应文档，不引入与需求无关的重构。
